1# Inbound Carrier Sales: build description23For HappyRobot Logistics' business and IT review. This is a proof-of-concept submission candidate. The service and App improvements are local until reviewed and approved for rollout. Version 3 is live; Version 4 is an unpublished candidate. The release checklist is in submission.md.45## Customer problem and scope67The brokerage wants to automate repetitive inbound qualification, matching and negotiation while keeping a senior rep responsible for the booking decision. This candidate demonstrates that first leg through HappyRobot web calls, an integration service and a HappyRobot Apps operations screen. It does not establish production capacity, answer-rate improvement, reduced burnout or financial return.891. **Check authority.** Take an MC number, look it up in FMCSA, confirm the returned carrier name with the caller and distinguish refusal from an unavailable service.102. **Check the emailed code.** Send a code to the configured demo inbox and check what the caller reads back before discussing loads. This demonstrates the code gate and access to that inbox, not the caller's legal carrier identity.113. **Find and price loads.** Read available loads matching equipment and state-level lane preferences. Offer a price below the private ceiling, with at most three counter rounds across the call.124. **Record agreement.** Save one tentative reservation at the agreed rate. The agent speaks a mocked handoff to a senior rep. A reservation is not a final TMS booking.135. **Rep review.** Show the captured carrier, shipment details, pickup/delivery, posted and agreed payment, negotiation activity and next action. Only the rep's Confirm can submit a booking request. Sends off or unknown mode disables Confirm.1415## Rules and boundaries1617The voice model requests actions; the service decides from stored state and fresh TMS reads. Authority, code checks, rate bounds, round counts, reservations and rep version checks are service rules. The model never receives the expected code or raw ceiling. Withholding the field prevents direct field exposure; it does not prove that offers reveal no indirect information. The load-specific cap makes exact inversion harder, while known policy bands still constrain possible ceilings.1819The TMS has no supported cancellation or idempotency key. A rep's Confirm rechecks the load and ceiling, wins a version-checked state change, then sends once. A timeout or incomplete result is unknown and is never resent. A complete reference-bearing PENDING receipt is an acknowledgement, not final confirmation. No live BOOKED receipt has been observed. No inventory quota or permanent consumption guarantee is inferred from those observations.2021## What operations can inspect2223Twin stores structured service activity: authority decisions, code delivery outcome, search criteria and returned public pitch details, each heard and normalized carrier ask, response and round, reservation and rep events, closing notes when supplied, and the workflow end report when delivered. State and its event are written together in the same row.2425This is sufficient to reconstruct service decisions without raw platform logs; it is not a verbatim recording or proof of what was spoken. Missing notes are shown as missing. End capture depends on the workflow reaching its callback and Twin accepting it. Pre-tool calls become visible after Version 4's callback is deployed and published successfully. No external database or general-purpose logging framework is used.2627The App separates real and test calls. Its metrics count recorded calls, reservations, rep approvals, pending acknowledgements, final confirmations, unknown outcomes and unmatched demand. The northstar is recorded reservations per call that ever passed its code. Tool-to-offer time begins at the first service request, excluding greeting and spoken delivery. Complete definitions and missing-data behavior are in kpis.md. Carrier payment and concessions are not brokerage revenue or profit.2829## Evidence3031The layered package in qa-package.md separates service tests, seeded generated inputs, conversation checkpoints, complete HTTP journeys, native model simulations and human voice calls. Current raw totals, versions, failures and reruns are in qa-results.md; they must accompany any presentation of success.3233One earlier real-integration call reached agreement and a rep Confirm whose TMS reply was PENDING. The owner's Version 3 transcript also shows name confirmation before code delivery, unmatched searches, an agreement through negotiate, a mocked handoff and clean close. The Version 4 candidate's E7 continuation passed eight repetitions, with ten additional continuation/regression checkpoints passing. The standard full text simulation reached a truthful handoff; the pressure simulation held verification but ended by idle timeout without closing notes. These small samples do not prove broad reliability. Human voice acceptance of Version 4, interruptions and final published-App visual review remain release checks.3435## How it runs and who owns what3637| Component | Location | Responsibility |38|---|---|---|39| Voice workflow | HappyRobot | Web-call conversation and six service tools; Version 4 adds the post-agent end report |40| Carrier Sales Service | Python 3.12 Docker container on Fly.io | Rules, FMCSA, code email, raw-TCP TMS adapter, Twin writes and rep actions |41| Twin | HappyRobot | Call and booking rows, each with its own event history |42| Operations App | HappyRobot Apps | Authenticated review, metrics and rep decisions through the service |4344After one-time cloud and secret setup, make deploy builds and deploys the container to the approved Fly environment.
