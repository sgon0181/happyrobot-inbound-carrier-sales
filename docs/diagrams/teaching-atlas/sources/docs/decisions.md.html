1# Decisions23Every design decision, why it was made and what it costs. [ARCHITECTURE.md](../ARCHITECTURE.md) describes the result; this file explains the choices. Numbers from the prototype are measured unless marked as estimates. Sources are the two audits in [audits/](audits/) and [lessons from the prototype](lessons-from-prototype.md).45## Decisions made on 2026-11-0267The owner approved D-22 to D-25, D-29, D-31 and D-32 on 2026-11-02, and later that day changed D-28 from a cap to a guideline. They follow from a prototype that worked but ran to 4,501 production lines, and the owner's requirement to understand every file handed in.89### D-22: `LOAD_BOOK` is sent at the rep's Confirm, not during the call1011Replaces D-8.1213- **Why:** the TMS has no cancel and no idempotency key. During a call, that send had to finish inside a 12 second request on a database allowing about 4 statements per second, while the carrier could hang up.14- **Evidence:** a hang-up during booking made the load unavailable on the observed token, a Twin failure after a real send left no stored reference, and in the model two bookings starting together sent nothing. On LD01094 a load was spent before the caller clearly agreed. The send path took 21 statements, and the code protecting it accounted for much of the size.15- **PDF fit:** the PDF reserves tentatively at agreement and has the senior rep confirm the booking. The handbook describes `LOAD_BOOK` as committing a booking. Luke left the timing to us.16- **Cost:** a booking failure appears after the call, so the rep calls the carrier back. The TMS shows the load `OPEN` until Confirm, so Confirm must re-check it. D-8's reasoning that `PENDING` reads as the tentative stage no longer applies; `PENDING` is now simply what the TMS returned.17- **Would change it:** a reply from Luke, or a rubric, requiring the send during the call.1819### D-23: Two tables, with each row holding its own events2021Replaces the nine prototype tables.2223- **Why:** Twin has no multi-table transactions, but one row updates atomically with a version check. Anything spread across rows can stop halfway.24- **Evidence:** three prototype failures came from this. Reservation spanned claims, a call freeze and a booking row. OTP consumption and call verification were separate writes. State saved first and its audit event afterwards, so an event could be lost. Of 70 statements per call, 13 were audit writes.25- **Book:** *Designing Data-Intensive Applications*: fields updated together can live in one document, which removes the need for multi-object transactions (p.287); conditional writes with a version number (p.302).26- **Cost:** events live in JSON instead of their own table. Rows are larger, and grow with repeated activity. No event-count maximum is proven; row size and retention need pilot measurements.27- **Rejected:** a same-row outbox with a projected `call_events` table, which both audits proposed. Nothing consumes that table, so it adds flushing, pruning and lag for no gain. The book's outbox (p.507) exists to decouple downstream consumers, and this system has none. Event sourcing (pp.103-104) was rejected for its replay and versioning cost.2829### D-24: A reservation is one booking row keyed by load ID3031- **Why:** the primary key gives one winner per load in one statement, which is the behaviour already proven on Twin (1 winner of 20 contenders).32- **Replaces:** the prototype's multi-table reservation layout. The booking row alone decides the holder, but one agreement per call still crosses the call and booking rows. Review found that the original no-claims argument was wrong. The implementation now uses an ID-bearing accepting claim, resolves it from booking history, and voids a stale claim through the booking row's own version-checked write before repricing. This is explicit recovery, not a multi-row transaction.33- **Cost:** one row per load, so a later attempt on a freed load carries earlier events forward.3435### D-25: Five things removed3637| Removed | Why it existed | Why it can go | Remaining risk |38|---|---|---|---|39| Transcript-reading consent check | A false yes could trigger a non-cancellable send | A false yes now creates a reservation the rep can decline. Each operation checks whether its effect already happened, so a repeat is safe without a fingerprint cache or a time window. The prototype's cache took about two-thirds of each call row. Platform retries were never proven to happen.4849### D-27: No background jobs5051Stale calls and stuck bookings are detected when read, and a rep resolves them. This removes the sweep loop, its silent failures and every shutdown question it raised.5253### D-28: Size is watched, not capped5455- **Was:** a hard cap of 1,500 production lines, so the owner could read every line.56- **Changed on 2026-11-02:** line count is a weak measure of quality. The owner now prioritises code that works, passes its tests and is understood at the level of what each part does, over reading every line.57- **What is enforced instead:** the gates in [architecture section 14](../ARCHITECTURE.md#14-quality), which are complexity, strict types, lint, branch coverage, one-way dependencies, and functions and modules kept short.58- **What stays:** every commit reports its production line count, so growth stays visible. Less code is still better when it is equally clear. Slice 1 used 646 lines.5960### D-29: Rebuild small on `main`, porting what is proven6162- **Why:** both audits judged the sound parts worth keeping. Most of the remainder exists because of D-8 and the multi-table design, so changing those decisions removes it instead of restructuring it.63- **Changes an earlier view:** both audits said refactor, not rewrite, and the Claude audit said to fast-forward `main`. Those verdicts assumed the same design. Two things are new: the design changes above, and the owner's requirement to read every file on a same-day deadline.64- **What carries over is behaviour, not code:** measured against [architecture section 14](../ARCHITECTURE.md#14-quality), none of the prototype's slice 1 code passes as written. No function has type hints, and the files show 115 lint issues and 95 strict type errors. So each piece is rewritten small, with the prototype's tests and recorded TMS replies as the check, and compared with the prototype on the same inputs before it is committed.65- **Not a fresh start:** the TMS findings, spent-load list, prompt, workflow, dashboard and evidence all carry over. `prototype/e2e` stays on the remote as reference.66- **Cost:** the prototype's live proof does not transfer. The new code needs its own real call, and at least one load.6768### D-30: The dashboard reads through the service6970The fallback for T-7 is now the design. The Apps gateway to Twin has been failing, and one path keeps every rule in one place. The ops key stays server-side.7172### D-31: Rep actions carry the version the rep saw7374- **Why:** a booking row is keyed by load ID, and a freed load can be reserved again by another call. Without this check, a rep on an out-of-date screen could confirm or release a reservation they never reviewed.75- **How:** the snapshot returns each booking's version. Confirm and decline send it back, and the service refuses if the row has moved on.76- **Cost:** a rep on an out-of-date screen is refused and has to refresh.7778### D-32: The second rule limits who can send, not when7980- **Why:** the earlier wording, "nothing irreversible happens during a call", did not match the design. A reservation exists before the call ends, nothing makes Confirm wait for it, and the code email is also sent during a call. What protects the TMS is that the voice agent has no route to `LOAD_BOOK`.81- **Cost:** a rep can confirm while the carrier is still on the line. The send runs outside voice cancellation, but the rep still owns the approval and the external outcome may be uncertain.82- **Also changed:** INV-1 now covers what the service returns and accepts, because the service cannot control what the model says.8384## Decisions made on 2026-11-038586### D-33: No fallback to the prototype8788- **Was:** if slice 4 was not working 4 hours before the upload, submit `prototype/e2e` with its limits disclosed.89- **Changed on 2026-11-03:** the owner chose to finish the rebuild, aiming for working software by 16:00 and recording the demo video that evening.90- **Why:** the owner would rather hand in code they stand behind than a prototype they never reviewed.91- **Cost:** if slice 4 runs late there is no finished fallback, and the owner would bring in Codex to help finish.9293## Earlier decisions9495| ID | Decision | Status |96|---|---|---|97| D-1 | One Python/FastAPI service | Active |98| D-2 | Twin is the only datastore | Active |99| D-3 | The service sends codes through an email provider | Active.
