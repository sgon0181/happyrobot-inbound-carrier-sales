The 2026-11-02 sandbox probe obtained a reference-bearing `PENDING` reply at `MAX_BUY + 1`, establishing no immediate ceiling rejection for that request, not final acceptance or the complete rate rule.204- **Cause of `PENDING`:** the handbook's successful `BOOKED` example uses MC 872144 and the same three payload fields, in the same order, as our inspected request construction: `LOAD_ID`, `MC_NUM`, `AGREED_RATE`. Some of our sends using MC 872144 and that request shape returned `PENDING`. Missing documented payload fields or a different field order therefore do not explain the observed difference; this does not rule out validation based on the field values.205206  The handbook's [LOAD_BOOK page](https://fde-challenge-candidate-handbook-production.up.railway.app/spec/load-book/) explicitly says the same load can resolve to different booking states for different tokens, intentionally. Captured `PENDING` values occupy the normal padded `STATUS` field, as `OPEN` and `BOOKED` do, and subsequent reads also reported `PENDING`. This supports a normal server status rather than a truncated or malformed injected reply. Padding alone cannot exclude every possible injected fault.207208  Across thirteen sends, we varied the load, carrier (inactive MC 872144 and active MC 138328) and rate, including `1`, equality with `MAX_BUY` and `MAX_BUY + 1`. Results were ten complete `PENDING` acknowledgements, two explicit errors and one `UNKNOWN`, with no observed `BOOKED`. Inactive authority cannot explain all the pending acknowledgements, and none of these tested variations established a `BOOKED` trigger.209210  Token-specific or server-side configuration is the leading working hypothesis, not an established diagnosis. All sends used one candidate token, which cannot isolate a token effect or distinguish configuration from undocumented server logic. [Q8](questions.md) asks Luke for clarification.
