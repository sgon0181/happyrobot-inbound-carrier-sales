## What changes for the desk

The service binds the operating terms to an offer and repeats the check at submission. A changed pickup ZIP, lane, appointment, equipment, commodity, weight, dimensions or notes requires a fresh agreement. The posted rate can change independently. The agreed payment must still fit the current ceiling. An older row without sufficient terms requires fresh review.

The App opens one combined Reservations workspace. All recorded calls and agreements appear by default; the Awaiting rep filter narrows it to current work. Overview uses the same records and links funnel stages and exception groups to their evidence. Progress includes ongoing calls, but loss groups require end evidence. Price pairs compare agreement against the caller's opening offer, not broker profit. Demand separates an empty search from never reaching search. Imported history stays view-only, including a previously released load.

Fresh recording links come from the dedicated workflow integration's immutable creation metadata and a valid native run ID. The server constructs the URL; callers cannot supply one. Known historical inventory remains a fallback for older records. UUID-only fixtures receive no invented recording link. This relies on keeping the agent key exclusive to that workflow, not on independently querying the platform to attest each run.

## Pilot configuration and rollback

1. Use an isolated HappyRobot workspace, Ops App and cloud service with separate Twin data, service keys and test TMS. Set TWIN_ENVIRONMENT=staging for isolated acceptance after provisioning calls and bookings in Twin staging. The default remains production for compatibility with the existing release. Also set CALL_COHORT=synthetic and LIVE_BOOKING=false for read-only TMS and voice acceptance. The service stamps the configured Twin environment on every SQL request. Set OPS_APP_ORIGIN to the App’s exact public HTTPS origin (for example https://carrier.example.test). If a deployed embed sends a distinct Origin, allow only its exact verified HTTPS origin in ALLOWED_ORIGINS. OPS_SERVICE_URL must point to the intended HTTPS service and HR_PLATFORM_URL to the platform that authenticates the App.
2. Set the App's server-only OPS_REP_SUBJECTS to a comma-separated list of exact subject IDs from platform-verified App users. Other users can investigate records. Even an administrator needs an assignment to mutate a booking. The audit event records the authenticated subject.
3. The approved demo sends email to the candidate inbox. For a customer pilot supply OTP_CONTACTS_JSON as a protected service setting containing independently verified MC-to-email mappings. For example, {"138328":"dispatch@example.test"} is a fixture. In roster mode an unlisted carrier receives no mail. New addresses require independent onboarding. The caller cannot change a destination. Delivery is capped at four attempts per recipient and 100 total per process every ten minutes, across all run IDs. Restarts reset this in-memory limit. Use shared provider throttling before scaling to multiple workers.
4. A booking-enabled service refuses to start without an enrolled roster. Confirmation also checks the OTP delivery proof on that specific reservation. For an isolated booking exercise explicitly set CALL_COHORT=real and LIVE_BOOKING=true on the proposal service. Use a fresh call to create a reservation. Historical synthetic and unclassified reservations cannot be sent. From the App open that reservation, compare its terms and call evidence, select **Confirm** and approve the request. Competing reps are checked against the version they reviewed.
5. A PENDING receipt with matching load, reference and valid timestamp is an acknowledgement. Only a matching BOOKED receipt yields final confirmation. After an ambiguous send, reconcile by reading and contact the TMS operator if needed. Reconciliation cannot write a duplicate booking or promote an inventory status to a booking receipt. To stop new sends, switch LIVE_BOOKING=false. The TMS has no documented cancellation for an accepted send.

The service builds with the repository Dockerfile. After provisioning an explicit isolated Fly target, native resources and secrets, run `make deploy APP=<proposal-app> APP_URL=<native-app-url>`. It deploys, checks authenticated readiness and opens that App. The command has no default cloud target. For source review without external business writes, `make review` opens a disposable local App. See [setup and limits](../reference/release.md#reproduce-the-application). Native App and workflow promotions are separate from this command. Before a candidate voice call, point its HTTP nodes at this matching isolated service and verify the final-offer flag binding. Promote the matching service and voice versions together after their acceptance checks.

## Reproduce the results

Run `make check` with Python 3.12. In ops-app run `npm ci && npm test && npm run lint && npm run build && npm run typecheck`. Run the concurrent booking scenario alone with `python -m pytest -q service/tests/test_peak_shift.py`.

Run `python -m service.tests.peak_profile` to measure MC verification with the actual 0.25-second Twin pacing setting, one dashboard refresh and a 12-second tool deadline. A new call now inserts the initial audit event and applies the authority result with a version check. A competing write forces a reread. Both events remain durable. These figures came from one local before/after run with a fake authority and Twin adapter and exclude voice latency.

| --- | --- | --- |
| 8 start together | 8/8, 8.29 s, 34 | 8/8, 4.02 s, 18 |
| 15 start together | 1/15, 12.01 s, 48 before deadline | 15/15, 7.53 s, 32 |
| 15 start 1.5 s apart | 15/15, 1.26 s, 62 | 15/15, 0.26 s, 32 |

On reviewed iteration `4f6bd51`, a separate full-flow burst with the same Twin pacing ran as follows: 12 isolated callers started together and requested the next tool immediately. Twelve authority checks succeeded. Eleven reached matching and zero of those eleven received an immediate agreement response within the voice deadline. The experiment used 184 SQL statements. Realistic voice think time and shared provider quotas need a separate measured pilot. A separate run staggered twelve arrivals by 1.5 seconds with three seconds between tools. All twelve verified and matched, but only six received an agreement response. Nine durable holds and six outstanding claims were observed. These are incomplete outcomes, not nine successful conversations.

To reproduce these full-flow experiments from a fresh clone, run `python -m service.tests.full_profile --arrivals 12 --spacing 0 --think 0`, then `python -m service.tests.full_profile --arrivals 12 --spacing 1.5 --think 3`. Each prints stage outcomes, SQL statements, durable holds and outstanding claims. The harness has only fake dependencies and loopback TCP, never submits a booking, and stops each caller on its first error without a terminal webhook. Timings and resulting counts can change with the revision and host. Run it separately from the deterministic suite.

The resulting repair requires a finalized source-call agreement, matching carrier, load, rate and trusted identity, before a rep can submit. A terminal webhook recovers an already held claim as needing carrier follow-up, or voids its claim ID so a late request cannot reserve after hangup. An incomplete hold remains releasable. It cannot be submitted or count as a reservation conversion. This repairs unsafe consequences of a timeout and does not establish peak voice capacity.

An offline replay over the historical 302-load inventory found 42 of the 50 then-open records passed the vocabulary and shipment plausibility checks. Eight required human review. Locations, commodities, dimensions and complete notes must match approved shapes. A prospective handoff also needs future pickup, a stable shipment, reachable TMS and current pricing. Those 42 historical records do not represent available stock today.
